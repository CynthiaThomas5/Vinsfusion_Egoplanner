# Nano D435i PX4 实机迁移 Agent 任务书

版本：2026-11-02。依据：[迁移方案](hardware-migration-plan-20261102.md)、[设备调查](../progress/evidence/hardware-inventory-20261102.md)、源码基线 `dbb724f`。本文把已选路线拆成可直接执行的模块；任务编号 HW01–HW14 固定。模块状态以 [CURRENT](../progress/CURRENT.md)、里程碑及各模块证据为准；任务书和计划本身不作为通过证据。

## 1 使用方式与执行规则

用户可直接发送：

> 按 docs/hardware-agent-workbook.md 完成 HW01。读取 CURRENT 和已有证据后直接实施，完成本模块全部出口；只验证受影响部分，写回结果。

需要连续执行时发送：

> 按 docs/hardware-agent-workbook.md 完成 HW01 到 HW06。在授权范围内完成一个模块就继续下一模块；常规可逆决策自主处理。现场动作缺失时完成可独立推进的部分，明确剩余条件，不假报通过。

恢复时发送：

> 继续当前实机迁移任务，沿用 CURRENT 记录的范围和模式，从未完成项恢复。

执行 Agent 必须遵守：

1. 先 `git status --short --branch`，读 README、GOAL、CURRENT、milestones，再读本模块卡片和其直接依赖的结果。已有用户修改保留。复用本机调查和旧实验记录，环境无变化时不重新盘点整个系统。
2. 足以实施就编辑和运行。开始只简述编号、缺口、产物、最小验证、范围与预算；不先另写一份总计划。模块内任务连续做完；用户授权连续范围时自动进入下一项，普通单模块请求完成该模块即可交接。
3. 普通推进按仓库30分钟/两轮探索约定拆有界子项；明确要求完成模块或范围时按Goal完成模式推进到指定出口，不在内部子项结束索要继续。不要自行调用持续Goal功能。
4. 一轮探索记录“假设、唯一主要变量、判据、结果”。同一代码/环境不重复验证；失败修根因，只复验受影响部分。连续无新增信息就改变有证据的方案或报告真实外部条件，不靠重启续跑。
5. 完成标准是本卡片核心行为可运行、关键数据正确、必需验证有结果。可选优化、全场景回归、长时间压力测试不自动成为前置。小改动不默认重跑全套仿真测试。
6. 控制出口、数据单位/时间/坐标、会话身份属于真实边界，必须正确；不要新增通用防御框架、第二份算法或与本次交付无关的功能。
7. 软件任务获授权后可完成本模块必要的源码修改、独立目录部署、构建和地面采集；沿用会话已有授权。拆桨、手持运动、供电与场地需要现场事实，只有依赖该事实的步骤等待；实际武装/飞行须在用户明确授权的试飞范围内。固件刷写、系统重装、清除旧工作区不属于默认迁移步骤。

任务书最初编制时尚未启动实现或飞行；此后的模块结果以各自证据为准。旧仿真GOAL作为历史验收契约保留；本实机任务不要求重新完成N01–N17。用户七项执行要求优先于旧路线中的可选重复次数、长时研究与流程建议。

## 2 默认技术边界与产物约定

- 主路径：Nano原系统Ubuntu20.04/Foxy，CPU运行视觉导航，独立工作区建议 `~/D435i-VINS-EGO-ROS2-hardware`。本地仓库为源码源头；远端不得成为无法回收的另一份实现。
- `~/realsense_debug`、`~/realsense_ros2_ws`和旧项目只读。使用旧驱动/库可先引用其固定路径；迁入源码或补丁时记录来源、基准commit、diff、SHA256、许可和验证范围，不覆盖旧安装。
- 当前D435i序列号 `243622073269`；旧相机 `035422071615` 的参数不能混入。既有HID-hold/sensitivity修复和候选IMU修正须核对实际加载链，不能重复校正。
- VINS/EGO继续使用 `dependencies/sources.json` 指定的唯一源码及现有补丁。第三方兼容改动加入 `dependencies/patches` 并登记应用顺序，不换算法分支来绕过问题。
- 相机输入统一 `/sensors/d435i/*`；定位沿用 `/localization/optimized_imu_odom`、`imu_odom`、`status`；规划沿用 `/position_cmd`；动作沿用 `/navigation/navigate_to_pose`；PX4控制仍仅由 `uav_px4_bridge` 发布。
- 原始VINS/地图采用连续局部世界与相机IMU参考点，epoch绑定。真实body坐标轴必须在rig中声明；把姿态转换到机体系是数值变换，不能靠改名。HW08统一规划参考点到PX4参考点的转换责任。
- 实机配置拟放 `config/hardware/`，入口配置拟为 `config/profiles/hardware.json`；单一rig文件拟为 `config/hardware/rig.json`。这些路径是待实现产物，目前不存在。简单路径参数即可，不开发配置管理框架。
- 新实机入口拟为 `tools/hardware.sh`，支持build、sensors、perception、plan、ev、control、status、stop。子命令随对应模块交付，未实现的命令应明确报错；下文是接口目标，不是假定已有可执行命令。
- 同一次运行复用run_id、epoch、配置快照。轻量结果 `progress/evidence/hwXX-<date>-<topic>.md`，原始日志/短包 `artifacts/runs/<run_id>/`；记录远端日志路径与必要文件哈希。无需为每条日志建立新验收系统。

## 4 HW01 ARM/Foxy构建与部署基础

**结果：** 当前固定VINS/EGO和所需own包在Nano完成实际构建，软件依赖能导入；此时不要求实机profile已能导航。

**入口：** `tools/project.sh`、`docker/Dockerfile.vins`、`dependencies/sources.json`、各包 `package.xml`/`setup.py`，重点是 `uav_px4_bridge/package.xml`、`uav_sim/package.xml`。

**动作：**

1. 创建独立实机目录，保存本地commit及相关未提交差异快照。只同步本项目需要的源码/配置，排除旧build/install、artifacts、凭据和私人目录。
2. 读取既有 `vins_integration/environment_manifest.json` 的Ceres2.1/OpenCV4.2与补丁来源，用实际库绑定确认可复用项。源码采用本仓库完整补丁组合，不能拿旧VINS二进制代替当前版本构建。
3. 提供ARM/Foxy构建入口，默认Release、低并发（先1个构建任务）。保留当前算法参数，不把编译适配与算法调整混做。
4. 修实际遇到的Python3.8兼容（如 `removeprefix`、`Path.is_relative_to`）、rclpy私有导入/API、C++头文件与Ceres差异。只动运行路径涉及部分；编译成功后还要执行Python导入/CLI冒烟。
5. 处理实机依赖闭包：`ros_gz_bridge`属于仿真启动，不能导致实机安装Gazebo。允许构建纯Python几何辅助包；用条件依赖或小范围拆分消除真实运行对Gazebo的硬依赖，不删掉仿真实际依赖声明。实机调用SDF的问题由HW03解决。
6. PX4消息暂按仓库版本构建用于接口检查；HW07读出真实固件后仅重建受影响包。保存实际构建包清单、工具链、依赖和成功命令。

**最小验证：** 一次所需包完整ARM构建，Python节点导入与入口加载。命令形式为 `colcon build --executor sequential --packages-up-to <实际目标包> --cmake-args -DCMAKE_BUILD_TYPE=Release`；实施Agent必须记录完整包名和真实环境，不把占位符当成功命令。修复后只重建失败包及其受影响依赖。

**完成条件：** 无缺包/ABI错误，能从干净shell source独立install并加载核心入口；已有库和新产物来源可追溯。新硬件launch尚未实现不阻塞本模块。

**遇阻：** 兼容修复若要求大范围改算法/降依赖，记录具体失败点后改评估ARM64 Jazzy CPU容器，只实施一条路径；不能直接运行amd64归档。两条路径均无可行结果时保持未完成，报告环境条件。

**产物/下一项：** 构建入口、依赖清单、HW01报告 → HW02。

## 5 HW02 D435i驱动和传感器接口

**入口：** Jetson既有 `start_stereo_rgbd_imu_hid_sensitivity_global.sh`、同名参数文件、`sdk2581-hid-hold-sensitivity`与 `ros2_hid_hold_ws`；本仓库 `config/components/simulation/d435i_bridge.yaml`仅用于核对话题契约，不作为实机驱动。

**动作：**

1. 锁当前相机序列号、实际加载SDK/wrapper版本和补丁；先复用旧脚本已解决的HID行为，启动前只检查目标设备占用。禁止盲目升级固件或循环USB reset。
2. 首个候选沿用640×480、IR/深度15Hz、gyro200Hz、accel100Hz；以设备实际支持/回读为准。RGB仅在需要关键帧时启用，关闭点云和深度对齐。投射器先沿用已有设置，有真实纹理/深度问题再做一个变量对照。
3. remap左右红外、合成IMU、原生深度及其CameraInfo到 `/sensors/d435i/*`。核对原始/矫正图像、左右内参、frame和IMU轴；双目frame相同的历史记录需查驱动语义，不直接交换左右或改标签。
4. 合成IMU按gyro采样时间插值；核对已有 `imu_corrected` 的修正责任，只应用一次。源timestamp保持驱动时间映射结果，不用收到消息的now替换。
5. 如果ROS输出16UC1，增加一个最小深度单位适配，输出32FC1米，保留原始stamp/frame/尺寸与无效值。单位取wrapper真实语义，区分SDK raw scale与ROS单位，禁止重复乘scale。
6. 新节点若确有必要，放在现有合适的own包并补entry point/依赖；只需remap的部分不新建节点。交付sensors子入口，退出仅关闭自身会话。

**最小验证：** 一次约60秒真实采集，记录左右配对数、实测速率、时间单调性、最大间隔、源龄、IMU有限值和静止重力方向；用一个已量距离的平面核对深度数量级。转换逻辑用已知单位样本及0无效值做定向检查。

**完成条件：** 两路图像、合成IMU、原生深度及CameraInfo可被ROS消费者连续读取，单位/时间正确，无重复占用或已知断流；此项不声称VINS精度通过。

**产物/下一项：** 相机参数、适配/remap、实际版本清单、60秒结果 → HW03。场景距离/重力姿态需现场提供；可先完成其余软件部分。

## 6 HW03 真实rig与session生成

**入口：** `tools/generate_vins_config.py`、`uav_sim/geometry.py`、localization `node.py`、mapping `adapter.py`、bridge `vio_ego_bringup.py`。旧候选：Jetson `vins_integration/config/`。

**动作：**

1. 建立唯一 `config/hardware/rig.json`，内容至少包括设备序列号、图像尺寸/矫正状态、左右K/D与基线、depth K/D和单位、IMU轴及修正链、IMU到各光学frame的SE(3)、相机/IMU时差、来源与版本。
2. 导入当前序列号的候选标定及来源哈希；保留PROVISIONAL事实。核对标定板尺寸、时差符号、图像是否已矫正；有确定错误就只重做该标定项。上游YAML/SDF数值不当作实机数值。
3. 给配置生成器和消费者增加显式实机配置路径。共享一个简单rig读取函数；同时列出并改完VINS生成、localization输入验证、mapping投影、planner内参和bridge安装读取处，避免一半真实一半SDF。
4. 生成新epoch的VINS YAML、左右模型、session manifest；记录rig/settings/generated files哈希，复用已有不可变session机制。真实配置明确 `known_zero_gyro_bias=0`；噪声和td使用有来源候选，不继承仿真零噪声假设。
5. 相机到真实机体安装变换与含桨包络可先标为未测，HW08使用前必须补齐。缺安装参数时允许手持定位/地图，不生成假的零外参让控制运行。

**最小验证：** 真实配置生成一次；检查左右基线、变换逆/组合和一个已知光轴方向；现有仿真生成器定向回归一次。无必要不重跑SITL。

**完成条件：** perception路径只读取该真实rig，所有输出使用同一标定身份；session可供VINS加载；未测安装项可见且无法误用于控制。

**产物/下一项：** rig、硬件VINS settings、生成器与消费者适配、来源清单 → HW04。

## 7 HW04 VINS与定位适配

**入口：** `src/vendor`中固定VINS、`dependencies/patches/vins`、`src/own/uav_localization/uav_localization/node.py`/`health.py`、硬件launch及VINS参数。

**动作：**

1. 用HW03生成的同一session启动当前补丁版VINS，复用原有优化/传播/telemetry接口；不启动旧checked adapter作为第二套定位出口。
2. 硬件节点 `use_sim_time=False`；localization直接使用系统ROS时间计算源龄、monotonic计算接收龄，不等待/伪造 `/clock`。保留epoch变化、时间倒退、源stamp单调性与frame一致性处理。
3. 真实IMU optical轴在rig中明确；优化位姿和传播位姿采用同一约定。核对上游速度表达系，按Odometry child约定转换线速度；角速度使用同一时刻、同一轴系的有效IMU观测，缺少偏置/协方差不得伪造零误差。
4. 增加实机定位新鲜度准入所需的最小路径，质量遥测仍如实输出。初始过期预算依据相机/优化周期及实际空窗确定并记录，不复制SITL时钟门，也不以放宽门限掩盖积压。
5. 先静止，再由现场人员缓慢做量测平移、升降、yaw与返回。出现显著漂移/跳变按输入配对、时差、轴向/标定、IMU修正顺序定位一个主要原因。

**最小验证：** 一次2–3分钟手持路线，报告初始化是否成功、优化/传播频率、源龄、位移与返回误差；一次地面停止VINS确认旧定位失效，新session不沿用旧epoch。相同片段可同时支持HW05，无需重复录包。

**完成条件：** 当前代码在真实输入下持续输出方向/尺度正确的局部里程计和真实状态，没有已知跳变/持续队列积压；初步误差和适用运动范围已记录。静止通过不能替代手持动态出口。

**产物/下一项：** localization实机路径、短包/报告、当前定位限制 → HW05。

## 8 HW05 深度建图与地图生命周期

**入口：** mapping `adapter.py`、`mapping_input.py`、`depth_gate.py`，`config/components/mapping/ego_input.json`，唯一上游 `plan_env`及其补丁。

**动作：**

1. 接入HW02的米制原生深度和CameraInfo，用HW03真实内参/外参、HW04优化位姿完成投影。深度与位姿保留同一源stamp，复用有界插值，不使用最新位姿代替采样位姿。
2. 只启动唯一plan_env地图实例；配置实际地面高度/局部地图范围，未知/占据规则沿用现有official_ego策略。无效深度不得清成free。
3. epoch变化/定位重启清除待融合队列、取消旧地图身份并确认reset；地图status反映实际融合，而非仅收到图像。
4. RGB关闭时不要求RGB-D关键帧作为深度融合前置；关键帧接口可保留但显式不产生。保持地图状态/快照/占据查询可用。
5. 对量测墙/箱回读raw和膨胀占据，检查表面位置/尺度及运动重影；先修标定/时间/单位根因，再谈参数调节。

**最小验证：** 复用HW04路线或一次短墙面扫描，输出一个带标定/epoch的地图快照与量测对照；一次epoch变化确认旧地图被清除。

**完成条件：** 障碍在正确方位和数量级被融合，地图持续更新，服务能读回，重启不拼接旧地图；不要求完整房间或高质量稠密重建。

**产物/下一项：** 实机mapping配置与适配、地图快照、误差/更新时间结果 → HW06。

## 9 HW06 EGO与导航任务接口

**入口：** `src/vendor/ego_planner`及补丁、bridge `vio_ego_bringup.py`、navigation `node.py`/`admission.py`/`task_state.py`、`ego_planner.json`、`task_supervisor.json`、`vehicle_envelope.json`。

**动作：**

1. 从真实rig传入深度内参/相机位姿，输入HW04里程计和HW05地图；保持现有EGO规划、traj_server与NavigateToPose，不再增加航点控制器。
2. 创建小范围实机候选参数：首版0.15–0.2m/s候选、约1m目标、足够空场；实际尺寸未知时仅计算，控制资格待HW08。膨胀与地图范围按真实包络/观测确定，不把0.299m仿真值视作实机标定。
3. 跑plan入口，输出 `/position_cmd` 但不连接真实控制发布。现有n08 compute_only只是topic重映射/桥保持，不等于完整EV-only；必须检查实际publisher graph。
4. 复用action的目标、反馈、取消和替换。实现量测/显示用的goal_id、epoch/map_id追踪；终点容差由后续试飞预算确定，不提前硬写“实机到达PASS”。
5. VINS重启、epoch变化时取消旧目标和轨迹；新会话不自动续任务。仅计算时action可以取消结束，不把没有真实移动的结果记为任务到达。

**最小验证：** 一个空场可行目标、一个取消/替换、一个直连被已测障碍挡住的规划目标；看实际曲线及地图占据，确认零PX4控制发布。无需全地图穷举。

**完成条件：** 真实地图驱动EGO产生可用轨迹，目标接口与取消路径工作，实时规划输出无持续积压。

**产物/下一项：** plan入口、实机planner/nav参数、曲线/接口结果 → HW07。

## 10 HW07 PX4识别与DDS通信

**入口：** `dependencies/sources.json`中PX4、px4_msgs、Micro-XRCE-DDS-Agent；bridge中的PX4消息导入和topic配置。

**动作：**

1. 通过已有可用的只读接口读实际固件、板型、DDS模块、串口用途、系统ID，备份参数。USB的FMUv5描述不是固件版本。保存可恢复的原参数文件。
2. 根据固件锁定匹配px4_msgs和Agent，核对状态topic版本后缀与字段。只重建受影响包；不同时启动MAVROS/另一控制桥。
3. 选择实际可用且不被GCS占用的USB串口或TELEM链路，设置必要通信参数并记录前后差异。物理UART接线、电平由现场按实板确认；固件缺模块且确需刷写时，先准备板目标/固件/备份再取得对应授权。
4. 启动Agent只读订阅状态、姿态、本地位置、timesync和所需EKF状态，不发布EV或任何模式命令。缺少某诊断DDS topic时优先用ULog补证，不为显示便利重编固件。

**最小验证：** 一次约60秒订阅，确认消息能解码、状态在更新、时间域可解释；定位尚未有效不是本模块失败。记录QoS及实际topic名。

**完成条件：** 真实固件/消息定义/Agent/串口匹配且回读稳定；PX4连接状态不能仅凭Agent显示client connected判定。

**产物/下一项：** 参数备份、通信/版本配置、真实topic清单 → HW08。

## 11 HW08 机体变换与真实时间

**入口：** bridge `vision_odometry.py`、`trajectory.py`、`time_mapping.py`、`px4_bridge_node.py`，HW03 rig及硬件frame/time配置。

**动作：**

1. 现场量测相机IMU相对飞控/约定机体原点的旋转和平移、机体含桨尺寸；记录轴定义、单位、变换方向。定位保留相机IMU参考点；EV明确转换到机体参考点，桥内处理杆臂，PX4相应EV位置参数不得再次补偿。
2. 统一转换位置、姿态、线速度和角速度，线速度包含旋转杆臂项；规划指令也转换到一致参考点。若轨迹无法提供完整姿态/角速度需求，明确低倾角候选近似并地面/悬停量测其误差，不能默认为严格等价。必要时在同一桥内统一规划参考点，不新增控制发布者。
3. 处理VINS局部初始yaw/原点与PX4 local的关系，复用现有对齐框架并核对全机姿态变换；不得通过真值或地理ENU假设偷换局部坐标。
4. 实现硬件系统时间路径：source stamp、ROS系统时间、monotonic、PX4 HRT的关系分别写清；核对实际固件DDS序列化同步，启用同步时按Agent时间域发送，避免再次手动加减偏移。
5. `timestamp`记录发送时间，`timestamp_sample`记录采样时间。真实源龄与接收龄分别计算，保留时间倒退/新epoch处理；不要求实机订阅 `/clock`，不删除所有时序检查绕过启动。
6. 给同一个bridge增加ev-only与control运行模式。ev-only仅允许EV输出，不创建或发布OffboardControlMode、TrajectorySetpoint、VehicleCommand；未使能control同样不会自动武装。

**最小验证：** 已知正前/左/上向量与yaw旋转、非零杆臂旋转、一个已知采样延迟的时间算例；实测Timesync记录对照；确认ev-only发布图中无三个控制输出。先完成离线/节点检查，真正EV融合在HW10验证。

**完成条件：** 参考点/轴向/时间映射正确且有可复算样例；硬件bridge可加载真实配置，不依赖SDF或Gazebo时钟。

**产物/下一项：** 真实安装配置、转换/时间代码及定向检查 → HW09。缺安装量测时先完成时间和模式代码，安装依赖保持未完成。

## 12 HW09 分层启动与完整负载

**入口：** 前述模块交付的launch和 `tools/hardware.sh`，各own包setup与配置路径。

**动作：**

1. 整合sensors→perception→plan→ev→control层级，避免各层重复启动相机、VINS或地图。一个session一套进程，保存会话PID/日志与退出信息即可。
2. 默认入口保持未武装；无自动16m目标、无仿真真值/完整世界地图、无Gazebo/SITL进程。status显示当前层级、epoch和实际进程状态。
3. 地面full-load使用相机、VINS、地图、EGO、nav以及bridge计算路径；桥的PX4输出采用显式关闭或隔离调试输出，保持相近CPU工作量，不能为了“算力通过”关闭规划/VINS。隔离方式必须在报告中注明。
4. 做一次5–10分钟完整负载，轻量统计优化/规划频率、队列趋势、源龄P95/P99/最大空窗、RSS、温度和CPU。按实际首批任务时长选时长并记明，不重复旧600秒静止实验冒充满载。
5. 有积压时先关闭可选RGB/显示/重日志，再根据测得瓶颈改线程或输入/局部地图；每轮一个主变量。给出初步任务时效预算及速度范围，不用降低健康要求换PASS。
6. stop只管理本会话。地面未武装可正常退出；实飞状态须先取消任务、按既定降落路径确认落地上锁，再停控制链。状态不明保留监护并报告。

**最小验证/完成条件：** 一次完整负载没有持续积压或已知时效违约；一次干净启动与停止能复现配置/日志，进程无残留冲突。只读PC显示属于可选，不以RViz性能阻塞本项。

**产物/下一项：** 可执行统一入口、负载报告与任务预算 → HW10。

## 13 HW10 拆桨EV融合及控制联调

**前置：** HW09；现场明确已拆桨、飞控供电稳定且可操作遥控器。Agent不能从串口状态推断桨已拆除。

**动作：**

1. ev-only启动，备份基础上设置当前版本必需EV融合/延迟/噪声参数；参数值取真实固件定义与量测，保留飞控自身IMU/气压计等必要源，不导入SITL预检豁免。
2. 现场移动前/左/上和yaw，读回PX4姿态/位置；用ULog检查EV aid实际融合、创新/拒绝、reset和local position有效性。输入topic有数据不代表已融合。
3. 在用户已授权的拆桨控制范围内检查心跳、设定点、模式命令应答、取消/退出与人工接管。拆桨台架不会真实升空，不能用takeoff完成门判断联调失败，更不能关闭高度检查伪造起飞成功；必要时提供明确台架模式，只验证相应通信/状态转换。
4. 地面停VINS一次、断Agent一次，确认旧定位/轨迹不再驱动控制，PX4按配置退出；记录 `COM_OF_LOSS_T` 与 `COM_OBL_RC_ACT`实际行为。不扩展成真实空中故障试验。
5. 把定位时效、机体尺寸、可用净空、控制频率/首飞速度/高度/到达容差填入首飞配置。达到首次试飞所需信息即可，不建立额外评分体系。

**完成条件：** EV真实融合、方向/尺度正确、局部状态可用；唯一控制发布者和人工接管/必要退出路径已验证，结束确认未武装。融合失败优先修时间/轴/参考点，不通过无依据增大噪声或放松创新门掩盖问题。

**产物/下一项：** 参数前后差异、ULog片段/报告、首飞配置 → HW11。

## 14 HW11 首次悬停

**前置：** HW10；用户明确授权本次试飞；现场人员确认基础机体可人工飞行、桨/安装/供电正常、遥控接管可用、空场足够。

**动作：** 按已冻结首飞配置启动；候选高度0.5–1m，先无目标保持约30秒，正常降落上锁。观察实际漂移、倾角、振动、源龄和PX4融合。明显偏移/定位异常时执行已有接管/退出方案，不在空中调坐标或临时改门限。

**最小验证/完成条件：** 一次实际保持、可观察的位置稳定、正常落地上锁，日志与现场观察一致。报告位移/漂移量和场地允许范围；一次成功只标首次悬停通过，不宣称长期/多场景资格。

**产物/下一项：** 悬停运行与落地状态、必要修正参数 → HW12。再次起飞须处于用户已授权的试飞范围内，范围已覆盖时不重复索要许可。

## 15 HW12 短距离目标

**入口：** 既有NavigateToPose action、HW06硬件目标配置、桥状态机。

**动作：** 约1m前向目标、0.15–0.2m/s候选速度，以HW10实际冻结值为准；执行到达保持→降落。先证明真实移动与停止，再加一个yaw或升降目标，返程/取消按现场条件安排。不要直接搬16m或柱群长航线。

**最小验证：** 一次前向目标完整闭环；用量测标记/现场视频等独立观察核对真实终点，记录action反馈、轨迹、PX4状态。只靠VINS自己报告回到目标不能证明真实到达精度。

**完成条件：** 实际位移、到达/停止符合冻结的本次小场景标准，正常落地上锁；可选三维扩展未做时明确范围，不阻塞已定义的前向首版。

**产物/下一项：** 短目标参数、独立到达与终态报告 → HW13。

## 16 HW13 静态障碍导航

**入口：** HW05地图、HW06 planner、HW08含桨包络与HW12跟踪表现。

**动作：** 先量测大净空单障碍，使起终点直连确实受阻；保证相机能观测运动方向，执行实际绕行、到达、降落。成功后再做两个错位障碍，保持同一基线和低速范围。膨胀必须容纳真实包络、定位/跟踪误差及停止所需空间；不沿用仿真“已取消净空门”作为真实安全论据。

**最小验证：** 单障碍一次、两个错位障碍一次；保存地图更新、实际轨迹/必要重规划、独立终点、无碰撞观察和落地上锁。只复验修改影响到的场景，不默认每场景三次或复跑N11–N17。

**完成条件：** 两种限定布局实际避障完成；仅单障碍成功则记录部分完成。动态障碍、窄门极限、玻璃/黑色表面泛化不在此出口内。

**产物/下一项：** 实测布局与运行报告、适用边界 → HW14。
