## 审查结论

1. **最新坏 RTT 会覆盖仍有效的同步状态。** hardware_ev.py:100 与 px4_bridge_node.py:480 直接保存最新 TimesyncStatus；SystemClockMapper.to_px4:101 检查该条 RTT。高 RTT 被拒后，直到下一条合格同步消息才恢复EV。控制 `_timesync_fresh`、`_px4_now_us` 与 `_publish_control` 采用同一最新样本语义，坏样本使心跳/设定点提前返回；未武装预发送状态机还会回到 DISABLED。
2. PX4 自身 Timesync.cpp:59 对高 RTT 拒绝更新滤波器，保留已有估计；TimesyncStatus 仍报告此次高 RTT。不能将“此次测量被拒绝”等同于“此前同步立即失效”。DDS 时间戳已经在 Agent 时域，不应再加一次 offset。
3. **EV detail 健康显示会停留在旧原因。** 无新 odometry 时，tick 不重算 health/source 有效性，仍显示上次 `ev_only`；首轮定位锁定后1815条 detail 仍是该原因，最后里程计接收龄91.77s。published计数不增长，底层没有重发旧EV；这是诊断状态失真。
4. 当前 PX4 EV 控制源要求正常输入间隔<200ms；无输入约400ms后停止EV融合（ev_control.cpp，2*EV_MAX_INTERVAL）。因此秒级EV断流具有实际影响。

## 修复决策

- **先做桥接器共享同步健康修复**：最新RTT继续如实显示；仅<=10000us且时域/新鲜度合格的样本可更新最近有效同步，坏RTT不得刷新其时间。此前合格状态仍在原2s范围时可继续使用，超过原2s、时钟跳变、epoch/时域异常仍拒绝。EV与控制使用同一判断，避免各自不同步。
- 同时修复EV detail在输入断源/health失效时仍显示ev_only的问题，按当前时刻和最近实际发布计数/时刻报告状态。
- VINS telemetry>0.615998s的生产/接收间隔须独立定位，保持门限，不用提高门限、重发旧姿态或忽略优化健康掩盖。
- **暂不修改固件调度。** 先完成桥接器修复及隔离/未武装回归，并解决定位源锁定；若仍有无法被原2s有效期覆盖的同步失效，或FC实际EV输入间隔持续异常，再评估固件调度。当前不能据此宣称闭环飞行资格。
