# GOAL C EGO Fast DDS reader history depth A/B #372–#377

- **问题**：#369–#371 已把目标 writer DATA 头关联到 EGO receive API，但早期 trace 只见部分样本进入 DataReader history。需确认实际 history QoS，并把 loopback DATA、EGO `recvfrom` 返回、Fast DDS reader hook按 sequence 对齐，区分队列容量与交付停顿。
- **方法与改动**：运行探针、EGO重建与所有源改动仅在 artifacts/runs；canonical 源码、参数与依赖锁未变。#375 读取运行时 DataReader QoS；#377 从 #345 run-local 源码仅将 pose subscriber QoS 25→100并通过5包构建。随后用已有 loopback RTPS header、EGO `recvfrom/recvmsg` DATA header、StatefulReader/DataReader history hooks 按 writer/reader GUID和sequence做离线对齐，没有保存PCAP或payload。Fast DDS `NotifyChanges`按每个writer的next sequence递增并在有序数据可用时通知 listener，见[2.14.6 StatefulReader.cpp](https://github.com/eProsima/Fast-DDS/blob/v2.14.6/src/cpp/rtps/reader/StatefulReader.cpp#L1107-L1164)。
- **结果**：
  - #372 的2.611 s gap中，sequence414首份DATA在loopback metadata的+1.447 ms可见，但EGO `recvfrom`仅在+2.610804 s返回同序号副本，StatefulReader随后处理并在+2.610907 s通知range[414,463]；depth未知时25条history仅保留[439,463]。
  - #375 的2.434 s gap中，50个sequence[254,303]经RTPS处理；运行时QoS为KEEP_LAST depth25。267/268/275/278首份包在loopback分别+0.674/+0.769/+1.062/+1.260 s出现，但EGO `recvfrom`仅在+2.4335 s收到同序号副本，之后listener范围[278,303]，history保留[279,303]共25条。gap内无成功pose take，sample-lost callback一次、rejected零次。socket drop计数+75，邻近等长窗+47/+27，仍是参与者socket全流量计数。
  - #377 同类2.410 s gap中，50条[500,549]全部进入depth100 history，但此前没有successful take。sequence500/509/542/547的首份DATA在loopback出现后未由EGO receive API返回；约+2.40925–+2.40959 s的同序号副本进入recvfrom，随后触发listener ranges[500,508]、[509,541]、[542,546]、[547,549]。socket drops+90（邻窗+48/+64），队列采样最高465,188 B；无sample-lost/rejected状态，32.5 s观察窗仍有335条freshness timeout。
  - #373 的 domain 233 超过 Fast DDS 可用端口计算上限232，传感器预检失败；#374 复制了已生成世界文件，生成器拒绝覆盖；#376 使用不含 #345 receipt hook 的旧 overlay，在 EGO 端点预检前退出24。三次均排除在运行结果之外并保留 run manifest。
- **结论**：depth25确实把这类50样本批次的DataReader history保留量限制为25，depth100可保留50；但两者都经历上游序列空洞与多秒take gap。按sequence对齐后，首份包在loopback出现而未见于EGO `recvfrom`记录，迟到的同序号副本到达后才进入Fast DDS并按序通知。participant socket drop与队列峰值支持接收侧压力为近端解释，但仍无法将aggregate drop映射到具体sequence，也未证明首份包为何未到用户态；单纯加深QoS不构成canonical修复。
- **边界与安全**：全局rmw-wait-summary wait序列连续性检查退出1；gap内按RTPS序号、capture、recvfrom和reader hook的定向对齐分析可复现上述迟到样本。SO_RXQ_OVFL及队列采样是socket级聚合，不能逐sequence归因。探针只记录元数据，不保存PCAP或应用payload。运行未发goal、未启动PX4或trajectory server，也未订阅truth/control；无轨迹执行、机体扫掠或飞行证据。
